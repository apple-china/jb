# 加贝云·化妆预约 V1.0 增量设计与文档差异

更新日期：2026-09-06（Asia/Shanghai）

## 1. 用途

本文把 [V1.0 确认需求基线](加贝云_V1.0_确认需求基线.md) 转换为相对旧 Mock 的开发差异。它用于限定改造范围和避免误用旧文档，不替代第三方接口字段契约。

文档优先级为：用户后续明确确认 > V1.0 确认需求基线 > 本文 > 更新后的技术设计/接口契约/覆盖矩阵 > 旧项目说明书、旧测试清单及旧 Mock 记录。

## 2. 必须替换的旧规则

| 范围 | 旧 Mock | V1.0 目标 |
|---|---|---|
| 角色 | 管理员/主播，可兼任 | 唯一超管、运营、观察员、妆造、主播；单账号单角色 |
| 登录 | 钉钉免登和测试身份 | 钉钉免登＋账号密码；至少一种登录方式 |
| 主播提前量 | 新建/取消30分钟 | 新建/取消20分钟，恰好20分钟允许 |
| 主播修改 | 不支持 | 老师/时间/团队可改，每预约日期最多成功3次 |
| 主播取消 | 按操作日1次 | 按主播＋预约日期累计2次 |
| 取消后资格 | 继续占用 | 立即释放，可重新新建；操作次数不清零 |
| 预约状态 | 有效/取消/作废 | 仅有效/已取消；不再提供作废 |
| 管理员时间 | 代约30分钟，修改/取消5分钟 | 代约1分钟；改时间原、新时间1分钟；仅换资源和取消无提前量 |
| 冲突 | 所有人均禁止老师重叠 | 主播禁止；超管、运营、妆造代约及管理员修改可带提示例外 |
| 排班 | 每日同一班次＋休息开关 | 周工作日＋单段班次＋启用/出勤；默认每日08:00—20:00 |
| 门禁签到 | 后续版本、6小时匹配 | 纳入V1.0；预约前后各120分钟（含端点、可跨天）；一条证据最多绑定一条有效预约 |
| 迟到通知 | 后续版本 | V1.0；仅催T＋10分钟仍无有效证据者，每预约最多一次 |
| 安排卡片 | 每日09:00定时 | 取消定时；首条有效预约自动触发或超管/运营手动触发 |

## 3. 账号与权限改造

- 用户只保存一个固定角色：`SUPER_ADMIN`、`OPERATOR`、`OBSERVER`、`MAKEUP`、`STREAMER`。
- 系统始终只有一名超管。应用内不得删除、停用、换角色、解绑或修改其登录标识；仅允许安全修改密码。IT恢复属于部署运维流程。
- 运营的预约修改、取消权限分别授权；运营不能创建或管理超管、运营，也不能给自己提权。
- 观察员只读且禁止导出。妆造可看排期、为本人代预约，不能修改或取消。
- 账号支持唯一钉钉ID、唯一用户名及密码凭据；至少存在一种登录方式。停用后旧会话立即失效。
- 无钉钉绑定的主播可预约，但界面必须提示无法自动签到和接收 @ 提醒。
- 密码、免登码、密钥不得进入业务日志；登录成功/失败、权限拒绝和凭据管理操作须留痕。

## 4. 预约数据与并发改造

- 预约状态收敛为 `ACTIVE/CANCELLED`。旧测试数据可整体重置，不开发 `VOIDED` 迁移兼容流程。
- 同一主播、预约日期仅限制一条 `ACTIVE`；取消记录不占资格。累计创建数量不设上限。
- 取消、修改次数须按 `streamer_user_id + booking_date` 分别累计成功次数，跨预约记录保留；失败、幂等重放、无变化修改不计。
- 主播新建/取消截止为开始前20分钟，边界包含；主播修改同时检查原、新开始时间。
- 管理员/妆造代约为开始前1分钟，边界包含。管理员改时间同时检查原、新时间；仅换老师/团队或取消无提前量限制。
- 管理员只处理今天、明天有效预约；管理员操作不改变主播次数。
- 主播冲突检查和计数更新必须在事务内串行化，避免多页面并发突破。管理员/妆造冲突例外须被显式记录和展示。
- 旧数据库的全局老师时间排斥约束不能直接沿用，否则管理员例外无法落库；改造时需采用能区分普通预约与冲突例外的并发方案，且不得使后续主播预约忽略已存在的例外预约。

## 5. 排班与出勤改造

- 老师增加按星期多选的单段班次；老师启用、出勤、工作日、完整20分钟处于班次须同时满足。
- 主播增加持续型出勤开关，由超管、运营维护，新账号默认开启。
- 团队启用、主播出勤、老师启用/出勤/班次是所有角色不可绕过的条件；只有时间冲突允许指定角色例外。
- 状态或排班变化只影响新建和后续修改，不自动取消已有预约。

## 6. 门禁、签到与提醒改造

- 魔点原始事件先验签、去重并保存，业务使用实际打卡时间。无匹配预约的事件也保留。
- 对每条有效预约查询同一主播在 `[T－120分钟,T＋120分钟]` 内的首次有效打卡，两个端点都有效并允许跨天。
- 签到状态为待签到、未到、已签到、迟到。无证据时T＋10分钟之前保持待签到，达到边界后转未到；证据不晚于T＋10分钟为已签到，晚于该边界且仍在窗口内为迟到。
- 改预约时间重算；仅换化妆师或团播组不重算。延迟到达的更早有效证据可纠正未取消预约并留痕，后续普通打卡不覆盖已签到或迟到结果。
- 取消时冻结签到快照，之后不再更新。一条门禁事件最多绑定一条有效预约，匹配时优先已开始预约，再按时间距离和稳定顺序确定归属；取消记录不占用有效预约的绑定资格。
- 已签到、未到、迟到均禁止修改，主播同时禁止取消，具备权限的管理角色仍可取消。待签到期间沿用原提前量；预约开始后至宽限结束前，管理角色仅能更换化妆师或团播组。
- 迟到卡片只催T＋10分钟仍无有效打卡者；已有迟到打卡只显示迟到。每条预约最多提醒一次，新预约独立计算。
- 历史业务数据切换时使用 `scripts/backup-and-clear-business-data.ps1`：先加 `-Preview` 查看目标行数，再执行脚本并输入数据库名确认。脚本停止后端写入、生成并验证 PostgreSQL 备份、事务清除预约及关联业务数据后恢复后端；账号、团播组、化妆师排班、钉钉绑定、系统配置和迁移记录保留。备份或验证失败时不得清除，脚本输出恢复命令且不随部署自动执行。

## 7. 安排卡片触发改造

- 删除固定09:00发送任务及相应告警口径。
- 预约日期第一条有效预约提交成功后，检查该群＋预约日期的卡片投放状态；从未成功投放则创建发送任务。今天首次提交明天预约，应立即触发明天卡片。
- 超管、运营可手动触发任意支持日期的安排卡片；手动可发送空安排，其他角色无此权限。
- 同一群＋预约日期只有一张当前卡片。已成功发送后，新建、修改、取消更新原卡；取消后再次出现首条有效预约不得重复创建。
- “待发送/重试中”不等于“已发送”。重试复用稳定业务键；失败不回滚预约。原卡确实失效且无法恢复时才创建替代卡。

## 8. 暂不实施及唯一待确认

- 不做调换、审批、自定义角色、实际妆造次数限制、复杂考勤、分段/跨夜排班、批量操作和门禁历史主动轮询；预约记录 XLSX 导出已按第七轮确认纳入。
- 当前测试数据可重置，无需旧数据迁移；Word项目说明书和Excel验收清单暂保留历史原件，开发相应模块时再定向产生新版验收项。
- 唯一待确认：超管、运营、妆造在代预约、修改、取消及冲突例外中，哪些操作必须人工选择原因。无论是否手填，系统日志均须记录操作类型、操作者、时间、对象和前后值。

## 9. 开发与验收顺序

1. 账号、单角色权限和密码登录。
2. 预约状态、资格、次数、修改和管理员冲突例外。
3. 周排班、老师/主播出勤和资源校验。
4. 魔点回调、签到、冻结、纠正和迟到提醒。
5. 安排卡片新触发方式及手动发送。
6. 更新模块级测试和覆盖矩阵；真实钉钉、魔点及群内 @ 联调通过后再出新版验收报告。
