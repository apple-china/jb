## 1. 设计范围与决策基线

### 1.1 目标

首版目标是交付一个简单、可靠、可验证的预约闭环：钉钉内免登，主播查看/创建/取消预约，管理员代预约/修改/取消/作废，指定群每天维护一张可更新的今日安排卡片。数据库是唯一事实源，第三方卡片或通知失败不得影响预约事务。

### 1.2 文档包同步结论

本文已吸收开发前独立审查中经核实的问题，并按《项目说明书 V1.0》完成同步。重点整改包括：统一预约状态常量；补齐管理员名单并发保护；明确老师/团队停用二次确认；规定门禁事件多候选的确定性匹配；扩充安全、回调、上传和生产禁用 Mock 的测试。钉钉官方 JSAPI Explorer 截至 2026-09-04 明确使用 `dd.requestAuthCode`，因此不改为其他命名空间。

以下首版边界作为实现基线：

| 项目 | V1.0 处理 | 后续版本 |
|---|---|---|
| 主播修改预约 | 不实现 | V2.0 重新评估 |
| 主播发起/确认调换 | 不实现 | V2.0 独立设计状态机 |
| 管理员直接调换 | 不实现 | V2.0；不在 V1.0 预埋半成品入口 |
| 管理员强制制造老师冲突或越班 | 不允许 | 如确有业务需要，另行评审，不建议默认开放 |
| 子管理员/分级权限 | 不实现 | V2.0 |
| 主播取消次数 | 实现取消日账本 | 按主播点击取消按钮的 Asia/Shanghai 自然日统计，每天最多成功取消一次 |
| 管理员账号 | 同级角色，可配置多人 | 至少保留一名启用管理员，无子管理员和分级权限 |
| 门禁、到司、迟到 | 不实现 | V1.1 |
| Excel、批量、复杂报表 | 不实现 | V2.0 |
| 每日卡片私有区“我的预约” | 实现 | 属于同一互动卡片接口的 `privateData` |

该基线使 V1.0 预约状态只有 `ACTIVE / CANCELLED / VOIDED`，无调换审批状态；数据库可直接用不可绕过的约束保证主播同日唯一、老师时段不重叠和主播取消日限次。

## 2. 总体架构

### 2.1 架构原则

1. 单体优先：一个前端工程、一个后端应用、一个 PostgreSQL 数据库。
2. 领域逻辑集中在后端：前端预校验只改善体验，不作为最终判定。
3. 业务与第三方解耦：预约事务提交后，通过数据库发件箱更新卡片或发送提醒。
4. 强约束下沉数据库：主播同日唯一、老师有效预约区间不重叠必须由数据库兜底。
5. 适配器隔离：钉钉和魔点均通过接口适配层接入，开发环境可替换为 Mock。
6. 不过度建设：V1.0 不引入微服务、MQ、Redis、分布式事务或复杂规则平台。

### 2.2 逻辑架构

```text
钉钉移动端 / PC端
        │ HTTPS + 会话Cookie
        ▼
Vue 3 H5（主播端 + 响应式管理端）
        │ REST/JSON
        ▼
Spring Boot 单体应用
├─ 认证与权限
├─ 预约领域服务
├─ 管理与审计
├─ 卡片编排器
├─ V1.1 门禁处理器
└─ 定时任务 / 数据库发件箱 Worker
        │ 事务 + 约束
        ▼
PostgreSQL
        │                 ├──────── 钉钉 OpenAPI / 互动卡片
        └─ 集成适配器 ────└──────── 魔点开放平台（V1.1）
```

### 2.3 模块职责

| 模块 | 主要职责 | 禁止事项 |
|---|---|---|
| Web 前端 | 钉钉免登发起、响应式页面、表单与友好提示 | 不保存 Secret；不自行决定权限或冲突结果 |
| Auth | 免登码换身份、创建本系统会话、角色识别 | 不把钉钉 AccessToken 当用户会话 |
| Appointment Domain | 可用时段、创建、取消、管理员修改/作废、状态校验 | 不直接调用第三方接口 |
| Admin | 列表、详情、基础资料、系统开关、审计查询 | 不提供物理删除业务历史 |
| Card Orchestrator | 聚合今日安排、公共/私有数据、发送/更新同一张卡片 | 不作为预约事实源 |
| Gate Processor（V1.1） | 验签、设备过滤、去重、匹配预约、记录识别事件 | 不因卡片失败让魔点重推业务事件 |
| Job Worker | 领取发件箱任务、重试、死信告警 | 不长时间占用预约事务 |
| PostgreSQL | 数据持久化、唯一性、区间排斥、幂等和任务锁 | 不保存明文 Secret/Token |

### 2.4 部署拓扑

V1.0 可部署为一个应用容器加一个 PostgreSQL 实例；Web 静态资源可由应用或反向代理提供。定时任务与 Worker 与 API 同进程运行，但代码模块隔离。若以后扩为多实例，通过数据库唯一键、`FOR UPDATE SKIP LOCKED` 和任务租约避免重复执行，无需先引入 Redis。

建议环境：

| 环境 | 第三方调用 | 数据 | 目的 |
|---|---|---|---|
| local | 默认全部 Mock | 固定夹具，可重置 | 开发与自动测试 |
| test | 钉钉/魔点沙盒或测试账号，可切 Mock | 脱敏测试数据 | 真机联调 |
| production | 真实接口 | 生产数据 | 正式运行 |

### 2.5 同步与异步边界

**同步完成后才向用户返回成功：** 身份与权限检查、业务校验、预约写入、审计日志、幂等结果、发件箱任务入库。

**事务提交后异步执行：** 每日卡片创建/更新、V1.1 迟到提醒、第三方失败重试。外部接口失败只影响通知状态，不反向撤销预约。

## 3. 核心业务流程

### 3.1 钉钉免登

1. 前端先访问 `/api/v1/me`；已有有效会话则直接进入。
2. 无会话时调用 `dd.requestAuthCode` 获取一次性 `code`。
3. 前端将 `code` 发送至 `/api/v1/auth/dingtalk-login`。
4. 后端缓存复用企业 AccessToken，调用钉钉换取 `userid/name`。
5. 后端按本地 `app_user` 判断启用的管理员/主播身份；管理员身份优先。
6. 后端签发本系统 HttpOnly 会话 Cookie，仅返回最小用户信息和权限。
7. 无角色用户返回 `403 USER_NOT_AUTHORIZED`，前端展示无权限页。

### 3.2 主播预约

1. 前端请求组合上下文 `/api/v1/booking-context?date=YYYY-MM-DD`。
2. 后端返回本人当日记录、当日公开安排、启用团队、可用老师和系统写状态。
3. 选择老师后请求可用时间块；前端禁用不可选时间。
4. 提交时带 `Idempotency-Key`；后端重新检查日期、提前量、资料状态、工作时间、同日资格和老师区间冲突。
5. 在同一事务中创建预约、名称快照、审计日志和卡片更新任务。
6. 数据库冲突统一映射为 409；前端提示该时间刚被预约。

### 3.3 主播取消

1. 只允许取消本人 `ACTIVE` 预约。
2. 系统写开关开启，且服务端当前时间不晚于 `start_at - 30分钟`。
3. 以取消操作发生时的 Asia/Shanghai 自然日作为 `cancel_day`；同一主播同一 `cancel_day` 最多成功取消一次。
4. 在同一事务中写入取消日账本并把预约更新为 `CANCELLED`；释放老师时段，但仍占主播该预约日期资格。
5. 同一幂等键重放只返回第一次结果，不重复计数；管理员代为取消不写主播取消日账本。
6. 同一事务写审计日志与卡片更新任务。

### 3.4 管理员操作

- 代预约：与主播新建使用同一硬约束；来源记为 `ADMIN`。
- 修改：只允许 `ACTIVE` 且距开始大于 5 分钟；日期不变；重新校验老师、团队、工作时间和区间冲突。
- 取消：只允许 `ACTIVE` 且距开始大于 5 分钟；转为 `CANCELLED`。
- 作废：`ACTIVE` 或 `CANCELLED` 可转为 `VOIDED`；释放主播当日资格；始终保留历史。
- 每次管理员写操作都必须提交原因，记录操作人、前后值、时间和请求追踪 ID。

### 3.5 每日卡片

1. 每日 09:00 按“群 + 业务日期”创建一张今日安排卡片。
2. 公共区显示全部有效预约，按起始时间升序；私有区按钉钉 `userId` 显示“我的预约”。
3. 卡片只有一个按钮“进入预约”，跳转微应用。
4. 当天预约变化后，仅更新原 `outTrackId`；连续变更合并为数据库最新快照。
5. 卡片不存在或已失效时，受控补发并把旧记录标记失效。

### 3.6 V1.1 门禁与迟到

1. 魔点向公网 HTTPS 回调推送成功识别记录。
2. 后端基于原始 Body 验签，校验机构、设备、事件类型并计算去重键。
3. `memberId` 按钉钉渠道规则直接匹配 `dingtalk_user_id`。
4. 事件先落库后匹配预约；找不到预约也返回 200 并保留异常记录。
5. 到预约开始 + 10 分钟仍无有效门禁事件时，创建唯一迟到提醒任务。
6. 迟到提醒使用新互动卡片并 @ 对应主播，不更新每日卡片代替提醒。

## 4. 数据库设计

### 4.1 数据设计原则

- PostgreSQL 以 `timestamptz` 保存瞬时时间，以 `date` 保存 Asia/Shanghai 业务日期。
- ID 推荐 UUIDv7；对外只使用不可枚举的 ID。
- 业务表保留 `created_at / updated_at / version`。
- 老师、团队和预约不物理删除；历史通过名称快照保持可读。
- JSONB 只用于审计前后值和第三方摘要，核心查询字段必须结构化。
- 所有表名、字段名使用小写下划线；状态使用大写英文常量。

### 4.2 实体关系

```text
app_user 1 ─── N appointment N ─── 1 makeup_teacher
    │                    │
    ├── N team（默认）    └─────── 1 team
    └── N streamer_cancel_ledger

appointment 1 ─── N audit_log
appointment 1 ─── N integration_job
appointment 1 ─── N gate_event（V1.1，经匹配）
daily_card 1 ─── N integration_job
```

### 4.3 `app_user` 用户与角色

| 字段 | 类型 | 约束/说明 |
|---|---|---|
| `id` | uuid | 主键 |
| `dingtalk_user_id` | varchar(128) | 唯一，字符串保存 |
| `display_name` | varchar(100) | 当前展示名 |
| `is_admin` | boolean | 同级管理员标识；无子管理员 |
| `is_streamer` | boolean | 主播标识 |
| `is_active` | boolean | 停用后所有角色立即失效 |
| `default_team_id` | uuid nullable | 最近/默认团队辅助字段，可不强制依赖 |
| `last_teacher_id` | uuid nullable | 最近一次成功预约的老师；仅作表单默认值 |
| `last_start_time` | time nullable | 最近一次成功预约的本地时间；仅作表单默认值 |
| `last_team_id` | uuid nullable | 最近一次成功预约的团队；仅作表单默认值 |
| `last_login_at` | timestamptz nullable | 最近登录 |
| `created_at/updated_at` | timestamptz | 审计时间 |

说明：同一用户可同时是管理员和主播，路由时管理员优先；业务接口仍按具体权限判断。V1.0 提供同级管理员名单维护，不提供主管理员/子管理员层级。新增、启用、停用管理员统一取得 PostgreSQL 事务级咨询锁 `jby:admin-membership`，再重新读取操作者、目标账号和启用管理员数量；变更后的启用管理员数小于 1 时回滚并返回 `LAST_ADMIN_REQUIRED`。咨询锁由事务自动释放，避免两个管理员并发停用时产生“零管理员”。

### 4.4 `team` 团队

| 字段 | 类型 | 约束/说明 |
|---|---|---|
| `id` | uuid | 主键 |
| `name` | varchar(100) | 当前名称，建议唯一 |

| `is_active` | boolean | 停用后不可用于新建/修改 |
| `deleted_at` | timestamptz nullable | 逻辑删除标记；V1.0 UI 优先用停用 |
| `created_at/updated_at` | timestamptz | 审计时间 |

### 4.5 `makeup_teacher` 化妆老师

| 字段 | 类型 | 约束/说明 |
|---|---|---|
| `id` | uuid | 主键 |
| `name` | varchar(100) | 老师名称 |
| `avatar_url` | varchar(500) nullable | 头像地址 |
| `work_start` | time | 当日上班时间 |
| `work_end` | time | 当日下班时间，必须晚于上班时间 |
| `is_resting` | boolean | 休息时不可产生新安排 |
| `is_active` | boolean | 停用时不可产生新安排 |

### 4.14 V1.1 `arrival_record` 与提醒去重

迟到提醒使用 `integration_job.business_key = appointmentId|LATE_REMINDER` 唯一约束，并在预约表或独立通知记录中保存 `late_reminder_sent_at/out_track_id`，保证重试不重复通知。

## 5. 状态机与规则引擎

### 5.1 预约状态机

| 当前状态 | 操作 | 新状态 | 角色 | 前置条件 |
|---|---|---|---|---|
| 无 | 新建 | `ACTIVE` | 主播/管理员 | 日期、提前量、同日资格、老师/团队状态、工作时间、冲突均通过 |
| `ACTIVE` | 主播取消 | `CANCELLED` | 记录本人 | 系统开启；当前时间 ≤ 开始−30分钟 |
| `ACTIVE` | 管理员取消 | `CANCELLED` | 管理员 | 当前时间 < 开始−5分钟；原因必填 |
| `ACTIVE` | 管理员修改 | `ACTIVE` | 管理员 | 日期不变；当前时间 < 开始−5分钟；全部硬约束重检；版本一致 |
| `ACTIVE` | 管理员作废 | `VOIDED` | 管理员 | 原因必填 |
| `CANCELLED` | 管理员作废 | `VOIDED` | 管理员 | 原因必填；释放主播日期资格 |
| `CANCELLED/VOIDED` | 其他普通操作 | 不变 | 任意 | 返回 `APPOINTMENT_TERMINAL` |

不提供恢复状态。误取消需要管理员作废原记录，再新建一条，历史链路清晰。

主播取消还必须满足：取消点击日尚无 `streamer_cancel_ledger`。若主播今天先取消明天的预约，今天不能再成功取消其他预约；跨过 Asia/Shanghai 00:00 后进入新的取消日额度。

### 5.2 可预约规则

```text
允许创建 =
  角色允许
  ∧（主播操作时系统写开关开启）
  ∧ 日期属于今天或明天
  ∧ start_at 按 10 分钟对齐
  ∧ now <= start_at - 30分钟
  ∧ end_at <= 老师当日下班时间
  ∧ 老师启用且未休息
  ∧ 团队启用
  ∧ 主播同日无非作废记录
  ∧ 老师 ACTIVE 占用区间不重叠
```

管理员代预约也必须遵守以上资源硬约束；管理员身份仅绕过“系统写开关”，不绕过提前量和冲突。若业务确认管理员代预约需要绕过 30 分钟，应单独增加明确规则与验收，不在实现中暗藏例外。

### 5.3 默认日期与默认值

- 今天存在至少一个满足提前量、老师工作状态和空闲区间的时间块时默认今天，否则默认明天。
- 老师、时间、团队来源于该主播最近一次成功预约保存的偏好；仅在当前日期仍满足启用、班次、提前量和不冲突时自动选中。
- 上次时间合法时自动选中；已冲突、已过期或不足提前量时清空并说明原因。
- 默认值永远不能绕过提交时的后端重检。

### 5.4 到司状态机（V1.1，派生状态）

为避免定时更新大量记录，到司状态优先由 `arrival_record + 当前时间` 查询时派生：

| 条件 | 展示状态 | 说明 |
|---|---|---|
| 预约已取消/作废 | 不适用 | 不参与迟到判断 |
| 有门禁记录，`arrived_at <= start_at + 10分钟` | 已到司 | 可同时显示到司时间 |
| 有门禁记录，晚于宽限时间且不晚于 `end_at` | 迟到 | `late_minutes = floor((arrived_at-start_at)/分钟)` |
| 无门禁记录，当前时间 ≤ `start_at + 10分钟` | 待验证 | 不能提前判定未到 |
| 无门禁记录，当前时间 > `start_at + 10分钟` | 未检测到门禁记录 `NO_GATE_EVENT` | 不是考勤结论；仅说明系统未收到记录 |

同一门禁事件出现多个候选预约时，必须使用以下固定规则且只关联一条：

1. 候选范围：同一钉钉用户、预约状态为 `ACTIVE`，且 `recognized_at` 位于 `[start_at - GATE_LOOKBACK_HOURS, end_at]`；晚于预约结束的事件不自动匹配。
2. 优先选择已经开始的预约，按 `start_at` 降序取最近开始的一条，记为 `STARTED`；是否迟到再由 10 分钟宽限计算。
3. 若不存在上述预约，再选择识别时间之后的预约，按 `start_at` 升序取最近将开始的一条，记为 `NEXT_UPCOMING`。
4. `start_at` 相同时依次按 `created_at`、预约 ID 升序，确保重复执行结果一致。
5. 匹配事务先锁定 `gate_event`；`arrival_record.gate_event_id` 与 `arrival_record.appointment_id` 的唯一约束最终保证事件不可复用、预约只记录首次有效识别。

### 5.5 集成任务状态机

```text
PENDING → RUNNING → SUCCEEDED
              └→ RETRY_WAIT → RUNNING
                              └→ DEAD（超过最大次数或不可重试错误）
```

Worker 领取任务时写租约；进程异常且租约超时后可重新领取。参数/权限/模板错误直接进入 `DEAD` 并告警，网络超时、HTTP 5xx 和平台忙进入指数退避。

## 6. 内部 API 设计

### 6.1 通用约定

- Base path：`/api/v1`；第三方回调：`/api/integrations`。
- JSON 使用 `camelCase`；日期 `YYYY-MM-DD`，时间 `HH:mm`，瞬时时间使用 ISO 8601 并含偏移，如 `2026-09-04T12:00:00+08:00`。
- 服务端忽略客户端传入的角色、主播姓名和快照名称，均从会话和数据库取得。
- 写接口要求 `Content-Type: application/json`、CSRF 头和 `Idempotency-Key`（创建/取消/作废等命令）。
- 资源更新必须带 `version`；并发版本不一致返回 409。
- 列表默认分页，`pageSize` 最大 100。

成功响应：

```json
{
  "success": true,
  "data": {},
  "traceId": "01J..."
}
```

失败响应：

  "success": false,

    "code": "TEACHER_SLOT_CONFLICT",

| `/actuator/health/readiness` | 数据库、迁移就绪 | 内网/编排平台 |
| `/actuator/metrics` | 指标 | 仅监控系统 |

健康检查不调用钉钉或魔点实时接口，避免第三方波动导致应用被错误摘除。

## 7. 权限与安全设计

### 7.1 角色

| 主体 | 识别方式 | 范围 |
|---|---|---|
| 管理员 | 本地 `is_admin=true AND is_active=true` | 管理端全部 V1.0 功能 |
| 主播 | 本地 `is_streamer=true AND is_active=true` | 本人预约命令和最小日程查询 |
| 其他员工 | 钉钉身份存在但本地无有效角色 | 仅无权限页 |
| 魔点回调 | HMAC 签名、机构和设备校验 | V1.1 单一回调入口 |
| 系统任务 | 进程内服务身份 | 卡片/提醒任务，不经过前台角色 |

### 7.2 权限矩阵

| 操作 | 主播 | 管理员 | 其他员工 | 魔点 |
|---|:---:|:---:|:---:|:---:|
| 查看本人预约 | ✓ | ✓ | — | — |
| 查看当日公开安排 | ✓ | ✓ | — | — |
| 创建本人预约 | ✓ | 可代预约 | — | — |
| 取消本人预约 | ✓ | ✓ | — | — |
| 修改预约 | — | ✓ | — | — |
| 作废预约 | — | ✓ | — | — |
| 管理老师/团队/系统开关 | — | ✓ | — | — |
| 管理同级管理员名单 | — | ✓ | — | — |
| 查看钉钉 ID 和审计 | — | ✓ | — | — |
| 写入门禁事件 | — | — | — | 仅签名回调 |

### 7.3 后端授权检查顺序

1. 会话有效且未过期。
2. 当前用户仍为启用状态；每次敏感写操作实时查询或使用短 TTL 权限缓存。
3. 当前接口具备角色权限。
4. 主播资源归属校验：`appointment.streamer_user_id == session.user_id`。
5. 预约当前状态和 `version` 符合命令要求。
6. 业务时间与资源硬约束通过。
7. 管理员名单变更在事务中锁定启用管理员集合；停用操作完成后至少保留一名启用管理员。

管理员名单写操作的具体实现：

1. 开启数据库事务并执行 `SELECT pg_advisory_xact_lock(hashtext('jby:admin-membership'))`。
2. 在锁内重新校验当前操作者仍是启用管理员，并读取目标账号最新状态。
3. 执行新增、启用或停用；随后重新统计启用管理员数。
4. 数量小于 1 时回滚并返回 `409 LAST_ADMIN_REQUIRED`，否则写审计日志并提交。

不得只使用“先 `COUNT` 再更新”或聚合查询 `FOR UPDATE`；它们不能可靠阻止并发产生零管理员。

前端隐藏按钮不是授权。任何通过浏览器修改请求、猜测 ID 或重放旧请求的行为都必须在后端失败。

### 7.4 会话与 Web 安全

- 使用随机服务端会话或短期签名会话，放入 `HttpOnly + Secure + SameSite=Lax` Cookie。
- 写接口校验 CSRF Token/自定义请求头；CORS 仅允许正式微应用域名。
- 会话建议 8 小时滑动过期，最长不超过 24 小时；管理员停用后敏感写操作立即失效。
- 登录接口按 IP、设备和用户维度限流；免登码不得入持久日志。
- 文件上传校验 MIME、扩展名、大小和图片解码结果；对象名由服务端生成。
- 响应设置 CSP、`X-Content-Type-Options`、`Referrer-Policy` 等安全头。

### 7.5 Secret 与日志

- Client Secret（企业内部应用对应原 AppSecret）、OrgAuthKey、AccessToken、机器人凭证放部署 Secret，不写 Git、数据库业务表或前端构建产物。
- HTTP 客户端对 Query 中的 `accessToken/orgAuthKey` 脱敏；日志不记录免登码和完整签名原文。
- 业务日志记录 `traceId`、接口编号、HTTP 状态、平台错误码、耗时和重试次数。
- 审计日志只能追加，普通管理员不能修改或删除。

联调配置使用以下固定环境变量名：

| 平台配置 | 环境变量 | 适用版本 | 管理要求 |
|---|---|---|---|
| 钉钉 CorpId | `DINGTALK_CORP_ID` | V1.0 | 受控标识；允许作为免登所需的前端运行时配置，不写死在源码 |
| 钉钉 Client ID | `DINGTALK_CLIENT_ID` | V1.0 | 企业内部应用对应原 AppKey；本项目不使用服务商 SuiteKey |
| 钉钉 Client Secret | `DINGTALK_CLIENT_SECRET` | V1.0 | 企业内部应用对应原 AppSecret；仅后端读取，本项目不使用 SuiteSecret |
| 魔点 OrgID | `MOREDIAN_ORG_ID` | V1.1 | 受控标识；第三方接口字段名为 `orgId` |
| 魔点 OrgAuthKey | `MOREDIAN_ORG_AUTH_KEY` | V1.1 | 高度敏感；仅后端读取，并对 URL、异常和日志脱敏 |

仓库仅保存无真实值的 `.env.example`。本地测试凭证放入 `.env.integration.local` 并加入 `.gitignore`；部署环境通过平台 Secret 注入。Mock profile 不读取这些真实值，integration profile 才允许连接测试应用。任何 profile 都不得向前端返回 Client Secret、OrgAuthKey 或 AccessToken。

## 8. 第三方集成与异步任务

### 8.1 适配器接口

业务层只依赖以下内部接口：

```java
interface DingTalkIdentityGateway {
  DingTalkUser exchangeAuthCode(String authCode);
}

interface DingTalkCardGateway {
  CardResult createAndDeliver(ScheduleCardCommand command);
  CardResult update(ScheduleCardCommand command);
}

interface MoredianGateway { // V1.1
  String getOrgAccessToken();
  void registerCallback(CallbackRegistration registration);
}
```

分别提供 `real` 与 `mock` 实现，通过环境配置选择；生产禁止启用 Mock 身份。

### 8.2 Token 缓存

- 钉钉与魔点 Token 在后端内存缓存，到期前 300 秒刷新。
- 同进程使用 single-flight/互斥，避免并发刷新。
- 下游明确返回 Token 失效时只强制刷新一次并重放一次。
- Token 获取失败不影响已登录会话的本地只读请求；需要第三方调用的任务进入重试。

### 8.3 数据库发件箱

预约事务中的最后一步不是调用钉钉，而是插入或合并 `integration_job`。Worker 提交外部请求后再独立更新任务状态。这样可解决“数据库成功、卡片失败”与“卡片成功、数据库回滚”的一致性问题。

任务领取示意：

```sql
SELECT id
FROM integration_job
WHERE status IN ('PENDING','RETRY_WAIT')
  AND next_attempt_at <= now()
ORDER BY next_attempt_at
FOR UPDATE SKIP LOCKED
LIMIT 20;
```

### 8.4 卡片更新顺序

`daily_card.content_version` 随预约变更递增。Worker 获取最新版本和最新预约快照，成功后写 `delivered_version`。若执行期间又产生新版本，任务完成后立即再排一次更新，保证旧内容不会最终覆盖新内容。

### 8.5 第三方接口契约引用

实现必须逐项遵循《加贝云_第三方接口契约_V1.0》中的 DT-01～DT-05、MD-01～MD-03，包括请求方向、成功判定、超时、幂等、重试、原始 Body 验签、回调去重和日志脱敏。技术设计不复制全部外部字段，避免两份契约漂移。

## 9. 可靠性、并发与异常处理

### 9.1 事务边界

创建预约的一个数据库事务必须包含：幂等记录占位、业务校验、预约写入、最近老师/时间/团队偏好更新、审计日志、卡片刷新任务。任何一步失败全部回滚。外部 API 调用不在事务内。

主播取消事务必须同时包含幂等处理、取消日账本插入、预约状态更新、审计日志和卡片刷新任务；其中任何一步失败均不得消耗取消额度或改变预约。管理员取消不写取消日账本。修改、作废使用相同事务原则，管理员修改通过 `version` 防止覆盖刚发生的取消或其他修改。

### 9.2 并发控制

| 场景 | 第一层 | 最终兜底 | 对用户结果 |
|---|---|---|---|
| 连续点击创建 | 前端按钮锁 + `Idempotency-Key` | 幂等表唯一键 | 返回同一预约 |
| 同主播不同请求同日创建 | 事务内查询 | 部分唯一索引 | 一个成功，一个 409 |
| 同主播同日并发取消两条不同日期预约 | 事务内取消资格检查 | 取消日账本唯一键 | 一个成功，一个 409 |
| 两人抢同老师重叠时段 | 可用时段预检 | PostgreSQL 排斥约束 | 一个成功，一个 409 |
| 管理员修改撞上他人新建 | 重新校验 + 版本锁 | 排斥约束 | 修改失败并刷新页面 |
| 卡片连续刷新 | 合并任务 | 内容版本号 | 最终展示最新数据 |
| 魔点重复回调 | 内存/请求级预检 | `dedup_key` 唯一键 | 重复事件返回 200 |
| 一条门禁事件命中多个预约 | 固定候选排序 | 事件/预约双唯一键 | 只关联一条且重复执行一致 |
| 迟到任务重复扫描 | 查询预检 | 唯一 `business_key` | 只发一条提醒 |
| 两名管理员同时停用 | 事务级咨询锁 | 变更后数量校验 | 至少保留一名启用管理员 |

### 9.3 边界时间

- “恰好提前 30 分钟”允许主播新建/取消：`now <= start_at - 30m`。
- “距开始 5 分钟及以内”禁止管理员修改/取消：要求 `now < start_at - 5m`。
- 老师 20:00 下班、时长 20 分钟，最晚开始 19:40。
- 所有比较在同一服务端时钟中完成；测试使用可注入 `Clock` 固定边界。

### 9.4 错误分类与重试

| 类型 | 示例 | 策略 |
|---|---|---|
| 业务冲突 | 同日资格、时段冲突、过截止 | 不重试，4xx，返回可操作提示 |
| 权限/参数 | 越权、模板错误、签名错 | 不自动重试；记录并告警 |
| 乐观锁 | 版本变化 | 409，刷新最新记录后由用户决定 |
| 临时基础设施 | 数据库短断、第三方 5xx/超时 | 有上限指数退避 |
| 结果不确定 | 卡片请求超时 | 复用原 `outTrackId` 重试，不生成新 ID |
| 永久第三方失败 | 权限不足、模板未发布 | 任务 `DEAD`，管理员可见且人工修复后重放 |

### 9.5 数据恢复

- PostgreSQL 每日全量备份并开启持续 WAL/时间点恢复（按部署能力）。
- 上线前验证恢复演练，不只验证“备份成功”。
- Flyway 迁移在发布前对生产快照演练；破坏性迁移采用扩展—迁移—收缩方式。
- 作废和停用均可审计，不通过物理删除“清理”错误数据。

### 10.4 并发与幂等测试

1. 50 个并发请求使用同一幂等键创建：数据库只有 1 条预约，所有成功响应引用同一 ID。
2. 两个不同幂等键为同一主播同日创建：只有 1 个成功，另一个为 `DAILY_APPOINTMENT_EXISTS`。
3. 同一主播用两个请求并发取消今天和明天的预约：取消日账本只允许一个事务成功，失败事务不得改变预约状态。
4. 两个主播同时抢同一老师同一时段：只有 1 个成功，另一个为 `TEACHER_SLOT_CONFLICT`。
5. 一个请求创建、另一个请求同时把目标老师设为休息：通过事务顺序得到唯一、可解释结果，不出现无日志写入。
6. 管理员打开旧详情后，预约已被取消，再提交修改：返回 `VERSION_CONFLICT` 或终态错误，不覆盖取消。
7. 两名管理员并发停用管理员账号：事务结束后仍至少保留一名启用管理员。
8. 卡片刷新任务并发执行：`delivered_version` 不倒退，最终内容对应最大版本。

| SEC-001 | 主播调用任意 `/admin/**` | 403 `FORBIDDEN`，无数据变化 |
| SEC-002 | 主播替换路径 ID 查看或取消他人预约 | 403 `FORBIDDEN` 或 404 `APPOINTMENT_NOT_FOUND` |
| SEC-003 | 请求体伪造 `streamerUserId/role/displayName` | 服务端忽略伪造值，身份来自会话与数据库 |
| SEC-004 | 写请求缺少或伪造 CSRF | 403 `CSRF_INVALID`，无数据变化 |
| SEC-005 | 非白名单 Origin 发起写请求 | 403 `ORIGIN_NOT_ALLOWED` |
| SEC-006 | 过期会话重放旧请求 | 401 `AUTH_REQUIRED`，幂等记录和业务数据均不新增 |
| SEC-007 | 管理员停用后复用原会话 | 403 `USER_NOT_AUTHORIZED` |
| SEC-008 | 扫描应用日志 | 不含 AppSecret、AccessToken、OrgAuthKey、免登码和完整签名 |
| SEC-009 | 魔点超限 Body 或畸形 JSON | 413 或 400，不写业务事件；验签比较使用常量时间算法 |
| SEC-010 | 图片伪装扩展名、非图片或超限 | 分别返回 `UPLOAD_FILE_INVALID` 或 `UPLOAD_FILE_TOO_LARGE` |

### 10.7 UI 与兼容性

- 重点视口：360×800、390×844、430×932；管理员另测 1366×768、1920×1080。
- 主播端单页不出现横向滚动；预约/取消用底部弹层；提交按钮始终可见。
- 管理端移动端用卡片/抽屉，PC 用表格/抽屉；同一功能不因端不同改变规则。
- 验证钉钉返回、刷新、网络切换、弱网重复点击、系统字体放大和长姓名。
- 生产部署验证 `/auth/mock-login` 路由不存在或返回 404，前端构建无 Mock 身份入口。
- 在钉钉移动端与 PC 端按官方 JSAPI Explorer 实测 `dd.requestAuthCode` 成功回传免登码。

### 10.8 质量门槛

- 核心领域规则与状态转换分支覆盖率不低于 90%；后端总体行覆盖率建议不低于 75%。
- 所有数据库迁移、并发用例、权限矩阵和第三方契约测试必须通过。
- 不存在 P0/P1 缺陷；P2 缺陷须有负责人和上线决定。
- 真机完成一次：免登 → 创建 → 卡片更新 → 取消 → 管理员作废 → 重新预约闭环。
- V1.1 上线前另完成真实门禁回调与真实群 @ 验收。

## 11. 部署、配置与可观测性

### 11.1 配置分组

| 分组 | 示例 | 管理方式 |
|---|---|---|
| 业务固定值 | 时间刻度、服务时长、截止时间 | 环境变量/配置文件，启动校验 |
| 钉钉 | CorpId、Client ID（原 AppKey）、Client Secret（原 AppSecret）、RobotCode、群 ID、模板 ID | Client Secret 放 Secret；其余按受控配置管理 |
| 魔点 V1.1 | OrgID、OrgAuthKey、设备 SN、回调 URL | OrgAuthKey 放 Secret；其余按受控配置管理 |
| 数据库 | URL、用户名、密码、连接池 | Secret |
| 安全 | 会话密钥、允许域名、上传限制 | Secret/配置 |

启动时必须校验环境组合：生产环境若启用 Mock、使用 HTTP 回调、缺少模板/群 ID 或固定参数非法，则拒绝启动或关闭对应集成功能并产生高优先级告警。

### 11.2 发布步骤

1. 备份数据库并验证 Flyway 迁移计划。
2. 部署后端，运行迁移，确认 readiness。
3. 部署前端并核对钉钉安全域名、移动/PC 首页地址。
4. 在测试群验证免登、卡片模板和按钮跳转。
5. 导入启用管理员、主播、老师和团队初始数据。
6. 打开系统写开关，执行核心冒烟测试。
7. V1.1 另执行魔点回调注册和一次真实识别验证。

### 11.3 指标与告警

| 指标 | 告警建议 |
|---|---|
| API 5xx 比例、P95 延迟 | 5 分钟持续超阈值 |
| 预约冲突 409 数量 | 观察异常突增，不作为系统故障 |
| 幂等重放/键冲突 | 异常升高时排查客户端重复提交 |
| `integration_job` 待处理数与最老年龄 | 最老任务超过 10 分钟告警 |
| `DEAD` 任务数 | 任意新增即告警 |
| 每日卡片 09:05 前未成功 | 高优先级告警 |
| Token 刷新失败 | 连续失败告警 |
| 魔点验签失败/UNMATCHED（V1.1） | 按次数和比例告警 |
| 迟到提醒去重冲突（V1.1） | 记录指标，确认无重复投放 |

### 11.4 日志关联

每个入口生成 `traceId`。预约 ID、任务 ID、`outTrackId` 和魔点 `dedup_key` 只记录必要摘要，使一次业务可从 API → 数据库事务 → 发件箱 → 第三方结果完整追踪。

## 12. 开发顺序与完成标准

### 12.1 推荐实施顺序

1. 建立仓库、环境配置、Flyway 和基础 CI。
2. 完成数据库表、约束和 Testcontainers 测试。
3. 完成领域规则、状态机、幂等和权限中间件。
4. 完成内部 OpenAPI 与 Mock 登录，前后端可独立联调。
5. 完成主播端核心闭环。
6. 完成管理端、审计和基础资料。
7. 完成数据库发件箱、每日卡片 Mock 与真实最小联调。
8. 完成全量自动测试、真机 UAT、部署文档和回滚演练。
9. V1.0 稳定后再进入 V1.1 门禁与迟到。

不建议让 AI 一次性无检查地生成全部前端、后端和数据库。应按以上垂直切片逐段实现，每段都运行测试、审查迁移和验证界面，再进入下一段。

### 12.2 Definition of Done

- 代码实现与本文 API、状态和权限一致，无 V1.0 范围外的半成品入口。
- OpenAPI 文件、数据库迁移、Mock、自动测试和部署配置全部进入版本库。
- 所有写操作有事务、幂等或版本控制；所有管理员写操作有审计。
- 真实钉钉免登、每日卡片创建、同卡更新和按钮跳转完成验收。
- 依赖第三方的失败路径经过模拟，预约主事务不受影响。
- 生产 Secret 未进入 Git；备份、监控、告警和回滚步骤可执行。
- 安全测试 SEC-001～SEC-010、资源停用确认、管理员并发和门禁多候选测试全部通过。

| ADR | 决策 | 原因 |
|---|---|---|
| ADR-001 | 单体 + PostgreSQL + 数据库发件箱 | 首版简单，仍能保证事务和异步可靠性 |
