# 动态复杂 Mock 数据集设计

## 1. 背景与目标

本设计为加贝云妆造预约系统提供一套可重复、可审计、随执行日期动态变化的 Local/Test 数据集，用于页面验收、接口联调、边界测试和缺陷复现。它不会改变生产数据库结构、公开 API 或预约业务规则，也不会把测试数据作为 Flyway 生产迁移发布。

目标数据规模如下：

- 今天 100 条预约、明天 100 条预约。
- 过去三天合计 100 条预约，按距今天 1、2、3 天分别生成 34、33、33 条。
- 10 个化妆师、30 个主播、10 个团队、1 个超管、5 个运营、5 个观察员。
- Local/Test 钉钉通讯录额外提供 50 个未注册员工。
- 覆盖有效、取消、修改、代预约、签到、登录、权限拒绝、异常、系统埋点、卡片投递与任务队列等差异化状态。
- 提供一键重置脚本；每次执行以数据库上海时区的当前日期和当前时间重新计算相对日期及时间戳。
- 提供 Docker 本地库、便携本地库、隔离测试库和生产库的只读/受控访问说明。

## 2. 约束与设计决定

### 2.1 预约数量与唯一约束

数据库的 `uq_active_appointment_streamer_date` 约束要求同一主播同一天最多一条 `ACTIVE` 预约。系统只有 30 个主播，因此今天和明天各 100 条预约采用以下合法分布：

- 30 条 `ACTIVE`：30 个主播各一条。
- 70 条 `CANCELLED`：同一批主播按轮转方式保留历史取消记录。

过去三天没有“必须有效”的要求，生成 34、33、33 条混合记录；较早日期包含 `ARRIVED`、`LATE`、`NOT_ARRIVED` 和已取消记录。所有预约时长保持 20 分钟，开始时间落在 10 分钟粒度，且 `booking_date` 与 `start_at` 的上海本地日期一致。

### 2.2 只保留最新 Local/Test 初始化 SQL

删除旧 `db/local/V2__mock_seed.sql`，以 `db/local/V7__complex_mock_seed.sql` 作为唯一 Local/Test 初始化数据源。V7 在 V1、V3、V4、V5、V6 完成后运行，因此直接使用当前字段名和约束，不保留旧结构兼容 SQL。生产迁移目录 `db/migration` 不增加测试数据迁移，因此生产 Profile 不会自动导入 Mock 数据。

由于旧 Local 数据库已经登记 V2，升级后必须执行一次新的本机安全重置。新重置会重建 Local/Test 的 `public` schema，让 Flyway 从空库执行生产结构迁移和最新 V7 数据迁移；不尝试兼容或保留旧 Mock 数据。

### 2.3 确定性标识与动态时间

生成器使用固定命名空间的 UUID、稳定用户名和稳定钉钉 ID，使测试断言和截图可重复；日期、预约时间戳、登录时间和审计时间戳则由执行时刻动态计算。SQL 开始时执行 `SET LOCAL TIME ZONE 'Asia/Shanghai'`，以 `CURRENT_DATE` 和 `clock_timestamp()` 为唯一时间基准。

重复执行采用“重建 Local/Test public schema，再执行全部当前迁移”的模型，从而保证数据只来自最新 SQL。脚本不会删除数据库本身、数据库角色或上传文件；测试会验证连续执行两次后数量不翻倍，并且第二次数据日期仍以执行日为准。

## 3. 组件与职责

### 3.1 动态 SQL 生成器

新增 `src/backend/src/main/resources/db/local/V7__complex_mock_seed.sql`，职责仅包括数据生成和数据库内断言。删除旧 V2 后，本文件是 Local/Test Mock 数据的唯一 SQL 来源。

SQL 使用 `generate_series` 和公共表表达式完成以下工作：

1. 验证上海时区日期，并确认当前 schema 为空的业务数据状态。
2. 生成当前版本所需的全部基础数据，不读取或兼容旧 V2 数据。
3. 生成 10 个团队，包含启用和停用状态、不同名称及占位图标。
4. 生成 10 个化妆师资源，组合不同工作日、上下班时间、排班启用、出勤和资源启用状态。
5. 生成 41 个系统账号：1 超管、5 运营、5 观察员、10 化妆师、20 个有钉钉身份的主播及 10 个仅密码登录的兼容主播。系统账号昵称、钉钉姓名和钉钉 ID 均保持唯一。
6. 为可预约测试生成的 30 个主播建立默认团队、最近化妆师和最近时间偏好。
7. 按 100/100/34/33/33 生成预约，并分配不同来源：`STREAMER`、`SUPER_ADMIN`、`OPERATOR`、`MAKEUP`。
8. 为部分预约生成 CREATE、MODIFY、CANCEL、ATTENDANCE_RECALCULATED 等审计记录；修改记录的 `before_data` 与 `after_data` 包含时间、化妆师、团队和冲突例外差异。
9. 生成操作计数、门禁事件、签到证据、迟到提醒、卡片记录、投递记录、调用日志、幂等记录和不同状态的集成任务。
10. 生成认证成功、认证失败、停用账号拒绝、代预约权限拒绝、参数校验失败、第三方错误和页面埋点等审计数据。
11. 在事务提交前用 `DO` 块断言关键数量、唯一性、外键一致性和预约分布；任一断言失败则整体回滚。

### 3.2 安全的一键重置入口

重写 `scripts/reset-local.ps1`，作为唯一一键初始化入口，负责选择运行时、保护连接目标、重建 Local/Test schema、触发 Flyway 并输出验证摘要。旧的 Docker 数据卷删除实现被移除，不再保留并行的旧初始化方法。

脚本支持：

- `-Runtime Auto|Docker|Portable`，默认 `Auto`。
- `-Database`，默认 `jiabei`。
- `-Force`，跳过交互确认，但不跳过安全检查。
- `-DryRun`，仅显示将连接的主机、端口、数据库、用户和预计生成数量，不执行写操作。

安全规则：

- 主机必须严格为 `localhost`、`127.0.0.1` 或 Docker Compose 服务 `db`。
- 端口只允许 Docker 的 `5432` 或便携运行时的 `55432`。
- Spring Profile 必须为 `local` 或 `test`；检测到 `prod`、生产 JDBC 变量、非本地主机或未知端口时立即终止。
- 执行前查询 `current_database()`、`current_user`、服务器地址和 Flyway 版本，结果必须与选择的目标一致。
- 未传 `-Force` 时要求用户输入目标数据库名确认；错误或中断保持事务回滚。
- 脚本不会调用 `docker compose down --volumes`，不会删除上传文件，也不会修改生产环境变量；它只会在安全检查和确认完成后重建目标 Local/Test 数据库的 `public` schema。

执行完成后输出账号、角色、团队、化妆师、五天预约、审计、门禁和卡片/任务数量，并打印常用本地测试账号。密码统一使用仅限 Local/Test 的明文编码值，生产 Profile 不加载这些数据。

### 3.3 Local/Test 钉钉通讯录

修改 `MockDingTalkDirectoryGateway`，以小型构造函数生成稳定的本地目录：

- 保留已注册系统账号对应的钉钉员工，维持既有登录和端到端测试兼容性。
- 额外生成 50 个未注册员工，ID 使用 `candidate001` 至 `candidate050`，姓名使用不重复的中文测试昵称。
- 搜索继续对姓名和 ID 做去空格、不区分英文大小写的包含匹配。
- 该实现继续受 `@Profile({"local","test"})` 限制，生产环境不暴露这些员工。

未注册员工不写入 `app_user`，从而真实覆盖“可添加的钉钉同事”列表，而不会破坏账号唯一性或角色数量断言。

### 3.4 数据库访问文档

新增 `docs/database-access.md`，提供以下方法：

- Docker Local：`127.0.0.1:5432/jiabei`，使用 Compose 中的本地账号。
- Portable Local：`127.0.0.1:55432/jiabei`，使用便携运行时本地账号。
- 隔离集成测试库：通过 `JIABEI_IT_JDBC_URL`、`JIABEI_IT_DB_USER`、`JIABEI_IT_DB_PASSWORD` 注入，不复用开发库。
- GUI 客户端、`psql` 和 JDBC URL 示例，以及安全的只读验证查询。
- 生产环境只说明从部署平台读取 `DATABASE_URL`、`DATABASE_USER`、`DATABASE_PASSWORD`，通过组织批准的 VPN/SSH 隧道访问；不记录真实凭据，不提供针对生产库的重置命令。

文档明确区分“打开数据库查看”与“执行 Mock 重置”，后者只适用于 Local/Test。

## 4. 数据分布

### 4.1 员工与资源

- 超管：1 个，启用，具有完整管理权限。
- 运营：5 个，混合代预约、修改、取消权限；至少 1 个停用账号。
- 观察员：5 个，至少 1 个停用账号，仅具只读能力。
- 化妆师：10 个，覆盖排班开启/关闭、五天/六天/七天工作制、早班/中班/晚班、出勤/休息、资源启用/停用及代预约权限开启/关闭。
- 主播：30 个，覆盖有/无钉钉身份、启用/停用、出勤/休息以及不同默认团队和上次预约偏好。
- 团队：10 个，至少 1 个停用团队。
- 未注册钉钉员工：50 个，仅存在于 Local/Test 目录网关。

### 4.2 预约与历史

- 今天：30 ACTIVE + 70 CANCELLED，共 100。
- 明天：30 ACTIVE + 70 CANCELLED，共 100。
- 昨天：34 条，包含已到司、迟到、未到和取消。
- 前天：33 条，包含修改后完成签到、代预约和取消。
- 大前天：33 条，包含不同来源及冲突例外历史。

为避免资源时间唯一性被业务查询视为冲突，ACTIVE 记录按化妆师和时间槽轮转；CANCELLED 历史允许复用时间。`conflict_override=true` 仅出现在少量由管理员来源创建或修改的记录中。

### 4.3 审计、异常与集成状态

审计记录至少覆盖：

- AUTH：`LOGIN_SUCCESS`、`LOGIN_FAILED`、`LOGIN_DENIED`、`PERMISSION_DENIED`。
- APPOINTMENT：`CREATE`、`MODIFY`、`CANCEL`、签到重算及冲突例外。
- USER/TEAM/MAKEUP_ARTIST/SYSTEM_SETTING：创建、更新、停用和权限变更。
- SYSTEM/TELEMETRY：页面访问、按钮点击、验证失败、后端异常和第三方网关错误。

集成数据覆盖 `PENDING`、`RUNNING`、`RETRY_WAIT`、`SUCCEEDED`、`DEAD` 任务，卡片 `PENDING`、`ACTIVE`、`FAILED` 状态，以及首次成功投递时间。所有状态值必须满足现有 CHECK 约束。

## 5. 清理范围与数据保护

所有生成实体使用稳定 UUID 和 `mock-complex-` 业务键。重置会删除并重建目标 Local/Test 数据库的 `public` schema，其中包括旧 Mock 数据和 `flyway_schema_history`；随后由 Flyway 重新执行当前生产结构迁移和唯一的 V7 Local/Test 数据迁移。

数据库本身、数据库角色、上传目录和环境变量不在清理范围。V7 继续创建既有自动化依赖的兼容账号 ID、用户名及钉钉 ID，但不保留旧 SQL 或旧数据。由于这是全量业务数据重置，安全入口必须先完成本机、端口、Profile、数据库名和现有 schema 身份校验，并在非 `-Force` 模式下要求用户输入数据库名确认。

## 6. 错误处理与可观察性

- PowerShell 使用 `$ErrorActionPreference = 'Stop'`，任何 `psql`/Docker 退出码非零都视为失败。
- SQL 包裹在单个事务中，并启用 `ON_ERROR_STOP`；断言失败不留下半套数据。
- 连接保护失败时打印被拒绝的主机、端口和数据库，但不打印密码。
- 成功时输出五天预约数量及 ACTIVE/CANCELLED 分布、各角色数量和审计/集成数据摘要。
- 测试失败保留隔离测试库供排查，不自动触碰开发库。

## 7. 测试策略

实现严格遵循测试驱动开发：先增加失败测试并确认因功能缺失而失败，再写最小实现。

### 7.1 PostgreSQL 集成测试

新增独立集成测试，迁移空测试库后执行 SQL 两次，并断言：

- 系统账号角色数量为 1/5/5/10/30，团队和化妆师各 10。
- 今天和明天各 100 条，ACTIVE/CANCELLED 各为 30/70。
- 过去三天分别为 34/33/33，总计 100。
- ACTIVE 唯一约束、外键、工作时段和枚举约束均通过。
- 包含四种预约来源、四种签到状态、修改/取消/代预约审计和五种任务状态。
- 第二次执行后数量不增长，所有动态日期仍相对数据库当前日期正确。
- 生产迁移测试仍证明 `db/migration` 不安装任何 Mock 账号。

测试数据库通过 `JIABEI_IT_JDBC_URL` 指向隔离库，禁止指向默认 `jiabei` 开发库；Docker/Testcontainers 可用时创建临时数据库，无 Docker 时明确跳过并给出运行命令。

### 7.2 Java 单元测试

为 `MockDingTalkDirectoryGateway` 增加单元测试：

- 额外员工恰好 50 个且 ID、姓名唯一。
- 未注册员工搜索可按姓名和 ID 命中。
- 保留既有员工兼容性。

### 7.3 脚本与手工验收

- `-DryRun` 不改变数据库。
- 对非本地主机、未知端口、生产 Profile 和不匹配数据库名逐一验证拒绝。
- 在隔离 Local/Test 库连续运行两次，比较摘要结果。
- 启动后在管理端验证列表、筛选、详情、修改历史、取消记录和添加钉钉同事。
- 使用 Swagger/SQL 查询核对今天、明天和过去三天的数量。

## 8. 验收标准

以下条件全部满足才视为完成：

1. 唯一最新 V7 动态 SQL、受保护的一键脚本、数据库访问文档和 50 人 Local/Test 钉钉目录均存在，旧 V2 与旧初始化方法已删除。
2. 隔离数据库实测得到约定的员工、资源、预约和历史数量，且重复执行幂等。
3. 今天/明天 100 条的设计没有绕过或移除 ACTIVE 唯一约束。
4. 审计、门禁、操作计数、卡片和队列数据可被现有页面或接口正常读取。
5. 生产迁移不包含 Mock 数据，一键脚本拒绝生产和远程目标。
6. 后端单元测试、PostgreSQL 集成测试及现有前端测试/构建保持通过。
7. 文档说明四类数据库访问方式，不泄露生产凭据，也不提供生产重置捷径。
